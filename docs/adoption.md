# Incremental adoption

`express-light-rail` is an installable set of independent Express/TypeScript mechanisms. It is not a host-app framework and is not a drop-in replacement for each application's base classes. Start with one seam, prove it in the consuming app's locked runtime and routes, and remove only the base implementation made redundant by that cutover.

## Ownership boundaries

| Owner | Owns |
| --- | --- |
| `express-light-rail` package | Exported controller/API action helpers, policy primitives, `BaseService`, `BaseSerializer`, `BaseJob`, `BaseApiError`, and opt-in API 404/error middleware. |
| Host application | Domain models and model initialization; routes; authentication/current-user context; resource authorization and permitted fields; transactions and persistence; serializer preload queries; job backend/workers; validation not explicitly adopted; module aliases, app startup, configuration, deployment and rollback. |
| MSSRT guidance | [Shared adoption/review doctrine](https://github.com/klondikemarlen/marlens-skills-rules-and-tools/issues/725) owns authoring, review, testing and workflow doctrine. It describes how to build host-owned features; it is not a runtime dependency or substitute for importing this package. |

Do not install application bootstrap, cloud credentials/helpers, `bin/dev`, Compose service names, gateway/DevHelper ownership, auth providers, queue persistence, or database lifecycle behavior from this package. Keep host middleware and route composition visible in ordinary Express.

All five audited controller implementations assume host authorization runs before action invocation; their base wrappers do not define each resource's authorization or association-preload queries. The package's `API` follows the Express action boundary and `next(error)` behavior, but does not provide the audited apps' `AuthorizedRequest`, `request.user`/`currentUser`, file, or format accessors; add only a thin host subclass that exposes existing request context. `BaseSerializer.requiredAssociation()` is a synchronous failure check, not a query/preload layer. Keep SQL joins and preloads with their existing host owner.

The legacy consumer service bases use generic inference backed by `any`; this package's generic `BaseService<TResult>` types `perform()` directly and the fixtures cover required, optional, no-argument, sync, and async signatures. Matching a declaration alone is not enough: verify package declarations with the locked compiler, real model types, and release artifact. WRAP additionally has an explicit request-abort middleware that attaches `signal` from request disconnect/unfinished response-close events; the other audited bases do not establish cancellation propagation. Pass an existing host `AbortSignal` only through the host's normal action/service boundary and prove it is respected before retiring a cancellation-capable base.

### Behavioral seams are not dependency ranges

- **Request context and auth:** the host establishes `currentUser` and other request-local data before controller actions. Package controllers accept Express requests and do not authenticate, attach users, or define policy. Preserve existing middleware order and authorization checks.
- **Errors:** API controller action wrappers forward thrown/rejected action failures through Express `next(error)`. This is Express error flow, not an application response contract. Install `createApiErrorHandler()` after API routes or retain the host's existing compatible handler. Do not return internal exception messages/stacks to clients. See [issue #2](https://github.com/klondikemarlen/express-light-rail/issues/2) for the error-middleware work; don't recreate it in an adapter.
- **Serializers/preloads:** `BaseSerializer.requiredAssociation()` checks a host-preloaded association at serialization time; it does not load associations. Keep query/preload decisions and domain shape host-owned, and test missing required associations explicitly.
- **Policies and collection filters:** policy authorization/scope remains host-owned. When combining visibility with a supported client filter, build the policy-scoped set first and apply client conditions as a further intersection; client input must never replace policy scope.
- **Construction and results:** base class inheritance preserves consumer constructors; `BaseService.perform(...args)` forwards them and returns `perform()`'s synchronous or asynchronous result. Type-check no-argument, required, optional and mixed constructor args in the installed consumer. `BaseSerializer.perform(record|records, ...args)` preserves its declared serialized result types.
- **Cancellation and transactions:** Express disconnect signals, transaction boundaries and cancellation behavior are not silently added by a base class. WRAP's source middleware creates/attaches `request.signal` for request abort/unfinished response close; preserve its middleware ordering and test through the actual host service boundary before replacing any consumer cancellation seam. Travel, ELCC, TK and Portal audited service/controller bases do not establish an equivalent propagation contract. Keep transaction ownership with the host.
- **Module format:** package metadata provides ESM (`import`) and CommonJS (`require`) builds plus declarations. Test both resolution paths against the actual packed artifact. This is not a claim that every host's legacy compiler, alias plugin, ORM or runtime can consume every export.

## Executable example

[`example-app/`](https://github.com/klondikemarlen/express-light-rail/tree/main/example-app) is a small in-memory Express app, not a fake database adapter. It shows normal `Router` composition, demo current-user middleware, host policy, mutation service, explicit serializer, safe error middleware and policy/client-filter intersection. Run from a repository checkout after installing peer/dev dependencies and building the package:

```sh
npm run example
```

Try the public behavior:

```sh
curl -H 'x-user-id: alice' 'http://localhost:3000/api/tasks?status=open'
curl -i -H 'x-user-id: alice' -H 'content-type: application/json' \
  -d '{"title":"Allowed","status":"open","visibility":"private"}' http://localhost:3000/api/tasks
curl -i -H 'x-user-id: bob' -H 'content-type: application/json' \
  -d '{"title":"Blocked","status":"open"}' http://localhost:3000/api/tasks
curl -i -H 'x-user-id: alice' 'http://localhost:3000/api/tasks?fail=true'
```

Alice's list request returns her open private task and excludes Bob's private task; changing `status` narrows, never widens, what the policy permits. Alice's mutation is allowed, Bob's mutation is a safe 403, and the deliberately thrown unexpected failure is a generic 500 response. `x-user-id` is demonstration-only, not production authentication.

## Consumer-shaped cutover fixtures and artifact smoke

[`tests/fixtures/adoption/`](https://github.com/klondikemarlen/express-light-rail/tree/main/tests/fixtures/adoption) keeps two disposable replacements: a Travel-shaped route/controller slice using the package API action base, and an ELCC-shaped service/serializer slice using package implementations instead of copying their base mechanisms. They are not application edits, forwarding shims, or proof that those apps have adopted a release. Both type-check constructor argument forwarding, inferred synchronous/asynchronous results, and exercise a real Express request/error path; the ELCC fixture additionally verifies that a required serializer association missing from a preload fails explicitly. The route fixtures retain host-owned authentication and policy decisions.

After the package owner has built and packed the candidate release, from the repository root run:

```sh
npm run build
npm pack
tests/fixtures/adoption/smoke.sh "$(pwd)/express-light-rail-<version>.tgz"
```

The smoke script installs that exact tarball and fixture-only dependencies into each isolated fixture, checks that the installed package version matches its tarball filename, records Node and package versions, type-checks and runs behavioral tests, then executes explicit ESM and CommonJS imports. Record the exact artifact filename/version and command output in the release review. For a published release, fetch the exact registry artifact with `npm pack express-light-rail@<version>` and run the same script in a clean fixture; a local source build or `npm pack --dry-run` is not published-artifact proof. These are verification recipes, not a claim that this document's edit has run them.

## Adoption sequence and rollback

1. **Pin evidence.** Capture the host's deployed Node version, manifest and lock-resolved Express/ORM versions; confirm package peer ranges and ESM/CJS/declaration resolution in the host's actual TypeScript config. Unsupported or missing runtime/ORM evidence blocks that seam, not the whole app.
2. **Pick one repeated seam.** Identify the exact duplicate base behavior and its callers. Compare public status/body, constructor signatures, return type, authentication context, policy ordering, preload contract, errors, cancellation and transaction boundaries before replacing it.
3. **Add an external fixture/test.** Install the packed candidate, replace the local base for one slice without leaving a forwarding alias, and exercise allowed/denied requests, unexpected errors, type inference, serialization and supported cancellation. Keep the ordinary Express router and host middleware.
4. **Review the diff and behavior.** Confirm no public response change, authorization widening, auth bypass, association lazy-load, query-filter widening, lost `next(error)`, swallowed cancellation, or dependency/runtime upgrade. Ask the owning application maintainers to review domain and migration semantics.
5. **Remove only superseded code.** Delete the copied base and references only after all in-scope callers use the package successfully. Do not remove unrelated controllers/services or establish an app-wide migration.
6. **Roll back by seam.** Revert that consumer slice and dependency/version change together if review or QA fails; keep the prior base implementation available in version control, not as a permanent alias. Preserve database, queue and deployment state using that host's own rollback procedures.

For error middleware, follow the supported contract delivered by [#2](https://github.com/klondikemarlen/express-light-rail/issues/2); for scoped reload helpers, follow [#3](https://github.com/klondikemarlen/express-light-rail/issues/3) and verify host ORM typing. This recipe intentionally does not restate either API or promise Sequelize 6 compatibility. No runtime upgrade, host write, release, registry install or application migration is implied.
